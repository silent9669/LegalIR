## 1. Executive Summary

This audit assesses the current state of the **LegalIR** repository at commit `70ada3b45544e21e805e6e184d7e3e702327d4f5`.

The repository contains strong foundational components for UIT Data Science Challenge 2026 Task 1 (Legal Information Retrieval), including canonical dataset creation (hierarchical macro/micro chunking with 8,532 documents, 1.15M chunks, 7,000 train queries), 4-branch candidate retrieval (BM25 micro, DEk21 dense macro, question memory, exact regex matcher), RRF fusion, cross-encoder reranking, and Codabench scoring compatibility.

However, the audit identified **four critical structural and algorithmic problems** that must be resolved to unlock high competition scores and reliable Kaggle T4 x2 execution:

1. **Critical Defect — Simulated Reranker Training:** `src/training/train_reranker.py` contains a stub that logs `status: completed` and writes `training_manifest.json` without loading model weights, calculating loss, performing backpropagation, updating weights, or producing a fine-tuned checkpoint.
2. **Notebook Drift & Monolithic Code Duplication:** `legalir_training.ipynb` (generated by `kaggle_kernel_task1/build_notebook.py`) embeds standalone copies of Python classes rather than importing or running repository modules. In doing so, it has drifted from the core code:
   - BM25 search extracts legal signals but **fails to apply legal boosts** in its scoring loop.
   - Tokenization is **inconsistent** (whitespace tokenization during corpus indexing vs. PyVi syllable segmentation during query search).
   - Evidence packaging statically slices the **first 2 macro chunks** in source order rather than performing query-aware intra-document chunk selection.
   - Dense DEk21 encoder is prematurely offloaded to CPU before train/public query embeddings are generated.
   - Validation reranking is evaluated on a **100-query-per-fold sample** rather than full 5-fold validation (1,400 queries/fold).
   - Only 1 GPU is targeted, ignoring Kaggle's dual T4 setup.
   - `torch` is re-installed in the notebook, creating environment instability.
3. **Architecture Duplication:** Two parallel, competing implementations exist in the repository:
   - Legacy stack: `src/common/` + `src/task1/`
   - Canonical stack: `src/retrieval/` + `src/ranking/` + `src/pipeline/`
   Scripts and tests inconsistently import from both stacks, causing dual maintenance overhead and subtle behavioral divergences.
4. **Huge Candidate-to-Ranking Score Headroom:** Historical benchmark records indicate:
   - Candidate Recall@150: **~97.35%**
   - Candidate Recall@50: **~94.42%**
   - Final Recall@5: **~75.36%**
   The ~22.0% gap between candidate recall and final top-5 recall proves that the candidate retrieval union is already capturing nearly all gold documents, and that **query-aware evidence localization + genuine supervised cross-encoder reranking + OOF fusion** is the highest-leverage path to maximizing official Recall@5.

## 5. Audit of `legalir_training.ipynb` and `kaggle_kernel_task1/build_notebook.py`

An in-depth code audit of `legalir_training.ipynb` and its generator `kaggle_kernel_task1/build_notebook.py` revealed several critical implementation flaws:

### 5.1 Embedded Code Duplication
The notebook contains ~1,200 lines of raw class definitions copied from `src/common` and `src/task1` across 13 code cells, violating single-source-of-truth principles and diverging from tested repository code.

### 5.2 Missing Legal Signal Boosts in Notebook BM25
In `kaggle_kernel_task1/build_notebook.py` Cell 4 (lines 346-373):
```python
signals = extract_legal_signals(query)  # Extracted here...
seg_query = tokenize_vietnamese(query.lower())
...
# Document-level score accumulation + legal entity boosting
doc_scores = defaultdict(float)

for idx, sc in zip(doc_indices, bm25_scores):
    ...
    doc_id = str(self.chunk_to_doc[idx])
    score = float(sc)

    if score > doc_scores[doc_id]:
        doc_scores[doc_id] = score  # But 'signals' is NEVER used here!
```
While `src/common/bm25.py` added boosts (`+30.0` for doc number, `+15.0` for `Điều`, `+8.0` for `Khoản`), the notebook extracted `signals` and then completely discarded them, losing high-precision statutory matching boosts.

### 5.3 Inconsistent BM25 Tokenization
- **Corpus Indexing (Cell 4):** `full_text.lower().split()` (whitespace splitting on raw lowercased text). Words like `hợp đồng` remain two separate tokens: `hợp` and `đồng`.
- **Query Search (Cell 4):** `seg_query = tokenize_vietnamese(query.lower())` followed by `bm25s.tokenize(seg_query)`. `ViTokenizer` produces compound tokens joined with underscores (e.g., `hợp_đồng`).
- **Result:** The query token `hợp_đồng` fails to match the indexed unigram tokens `hợp` and `đồng`, severely depressing BM25 lexical recall on compound Vietnamese legal terms.

### 5.4 Static Intra-Document Evidence Localization
In Cell 5 (lines 534-542):
```python
chunk_map = {}
for r in macro_df.groupby("doc_id").head(2).to_dict("records"):
    did = str(r["doc_id"])
    if did not in chunk_map:
        chunk_map[did] = []
    chunk_map[did].append({
        "article": r.get("article", ""),
        "text_raw": (r.get("text_raw", "") or "")[:1200]
    })
```
Every candidate document is represented for reranking by only its **first two macro chunks** in source order. For a legal document with 100 articles, a query asking about "Điều 85" will be reranked using Điều 1 and Điều 2, guaranteeing that the cross-encoder never sees the relevant evidence passage.

### 5.5 Premature Dense Model CPU Offloading
In Cell 5 (line 527), `dense.offload_to_cpu()` is called immediately after corpus encoding. When `global_memory.fit()` is called in Cell 6 and encodes training queries, it is forced to run on CPU.

### 5.6 Truncated Cross-Validation ("Fake CV")
In Cell 9 (line 1032):
```python
# Rerank & evaluate on validation sample (100 queries per fold for rapid CV)
rerank_sample_ids = val_ids[:100]
```
The notebook only reranks 100 validation queries per fold (out of 1,400 queries per fold), reporting a 100-sample metric as the fold CV. Full 5-fold CV over all 7,000 queries is never computed.

### 5.7 Sequence Length Truncation
In Cell 8 (line 810), the reranker hardcodes `max_length: int = 256`, whereas `configs/pipeline.yaml` specifies `max_length: 512`, truncating legal evidence passages in half.

### 5.8 Inefficient Hardware & Multi-GPU Usage
The notebook checks `torch.cuda.get_device_name(0)` and targets only a single GPU (`cuda:0`). On Kaggle's dual T4 setup (`T4 x2`), the second GPU sits completely idle.

### 5.9 Environment Instability (PyTorch Reinstallation)
In Cell 1 (lines 68-70), the notebook runs `pip install torch`, risking CUDA driver/runtime mismatches on Kaggle's pre-configured PyTorch environment.

### 5.10 Non-Deterministic Fallback IDs
In `TopKSelector` initialization, `fallback_doc_ids=list(valid_doc_ids)[:5]` takes a slice of an unordered Python set `valid_doc_ids`, producing non-deterministic fallback predictions across runs.

## 6. Audit of Parameter Counting, Official Scoring, and Submission Validation

### 6.1 Parameter Counting Logic
- **Constraint:** Total learned parameter count of every model across the entire Task 1 pipeline must be **strictly below 4,000,000,000 (< 4.0B)**.
- **Current Script:** `scripts/audit_parameters.py` checks:
  - `CODE4LIFEOFFICIAL/huydang-dek21-embedding-v2`: ~135,000,000 parameters (~0.135B)
  - `BAAI/bge-reranker-v2-m3`: ~568,000,000 parameters (~0.568B)
  - Total: ~703,000,000 parameters (~0.703B), well under 4.0B (17.58% of budget).
- **Missing Requirements:**
  - `scripts/audit_parameters.py` requires live internet access to download weights; it lacks an offline mode using `AutoConfig`.
  - It does not automatically export `parameter_audit.json`.
  - It must be structured as a hard-failing preflight gate in the pipeline.

### 6.2 Official Scoring Parity
- **Official Scorer (`Scoring-Program-Task-LegalIR/scoring.py`):**
  ```python
  recall = np.array([len(set(y_true[k]) & set(y_pred.get(k, set())))/len(y_true[k]) if len(y_pred.get(k)) > 0 and len(y_pred.get(k)) <= 5 else 0 for k in ids_truth]).mean()
  precision = np.array([len(set(y_true[k]) & set(y_pred.get(k, set())))/len(y_pred[k]) if len(y_pred.get(k)) > 0 and len(y_pred.get(k)) <= 5 else 0 for k in ids_preds]).mean()
  ```
- **Equivalence Check:**
  - `src/evaluation/evaluator.py` (`evaluate_predictions`) and `src/evaluation/codabench_compat.py` (`assert_official_equivalence`) mirror this exact logic.
  - Test `test_internal_metrics_equal_official_scorer` in `tests/test_codabench_compat.py` explicitly verifies numerical identity between the internal evaluator and the official scoring script.
- **Key Scoring Implications:**
  - `0 < len(pred) <= 5`: If a query has 0 predictions or >5 predictions, both Recall and Precision are set to **0.0**.
  - Duplicate predictions in `pred` penalize Precision because `len(y_pred[k])` in the denominator counts list length while the numerator uses `set()` intersection.
  - Since official ranking sorts by Recall first (Precision is only a tie-breaker), and 92.1% of training queries have 1 gold document (mean ~1.09 gold docs), **predicting exactly 5 unique relevant document IDs per query maximizes Recall**.

### 6.3 Submission Validation Logic
- `src/evaluation/submission.py` implements `validate_submission` and `package_submission`:
  - Enforces exact query key set equality (`pred_qids == expected_qids`).
  - Enforces `1 <= len(answer) <= 5`.
  - Enforces all elements are strings.
  - Enforces zero duplicate document IDs.
  - Enforces all document IDs exist in the canonical corpus document ID set.
  - Generates `submission.zip` containing **strictly `submission.json` at root** (no directory nesting).

### Headroom & Gap Analysis:
$$\Delta(\text{Candidate Recall@150} - \text{Final Recall@5}) = 97.35\% - 75.36\% = \mathbf{21.99\%}$$

- **Candidate Retrieval is already strong:** With 4 branches fused by RRF, 97.35% of all relevant legal documents are captured within the top-150 candidate pool.
- **Reranking & Selection is the primary bottleneck:** The existing untuned BGE reranker and static 2-chunk evidence packs only place the true positive in the top 5 for 75.36% of queries, leaving **~22% of retrievable queries unrecovered**.
- **Optimization Strategy:**
  1. Fix BM25 legal signal boosts & PyVi dual-branch tokenization to push Candidate Recall@150 past **98.0%**.
  2. Implement dynamic query-aware evidence localization (selecting the exact `Điều`/`Khoản` matching the query).
  3. Supervised fine-tuning of BGE Reranker v2 M3 on hard negatives mined from Task 1 data.
  4. OOF learned LightGBM / weighted RRF fusion over multi-branch rank & similarity features.
